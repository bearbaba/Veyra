# Veyra Phase 4D — Provider Activation Readiness

**Status:** implementation in progress on `phase4d-provider-activation`  
**Date:** 2026-10-10

## Goal

Phase 4D makes provider activation evidence-driven and fail-closed.

A provider cannot become executable because an adapter exists, documentation looks correct, or a model says the route should work. Fund-moving providers follow the lifecycle:

`DISCOVERED → VERIFIED → IMPLEMENTED → TESTED → ENABLED`

Promotion to `TESTED` requires real testnet execution evidence for every fund-moving capability. Promotion to `ENABLED` is a separate reviewed decision and additionally requires fresh runtime health.

## Locked rules

- No automatic manifest mutation.
- No `IMPLEMENTED → ENABLED` shortcut.
- Phase 4D testnet evidence cannot enable mainnet.
- Evidence must match the manifest adapter/package version.
- Evidence must include independently reviewable references.
- Bridge evidence additionally requires recovery and duplicate-prevention verification.
- Earn deposit/withdraw evidence additionally requires explainability verification.
- Earn review requires explicit withdrawal availability, delay, limits, fees, liquidity, APY provenance, yield mechanism and risk information.
- Multi-network providers must declare exact network ↔ asset compatibility.
- Fresh runtime health must be `OK` before `TESTED → ENABLED`.
- `DEGRADED`, `DOWN`, `UNKNOWN` or stale health cannot approve activation.

## Evidence ledger

Structured activation evidence lives in:

`src/providers/activation/providerActivationLedger.ts`

The Phase 4D ledger intentionally contains **no synthetic evidence**. Real E2E records are added only after execution and review. Git history provides the repository audit trail for those additions.

Existing providers that were enabled before the structured Phase 4D ledger retain their historical evidence in the provider manifest provenance; they are not silently rewritten into new Phase 4D records.

## Promotion workflow

### IMPLEMENTED → TESTED

Required:

1. Complete real testnet execution.
2. Verify final state.
3. Verify Veyra receipt.
4. Verify signature budget.
5. Record reviewable evidence refs.
6. Satisfy capability-specific evidence.
7. Obtain explicit `TESTED` approval **after** the E2E evidence exists.

The promotion gate returns a proposed state only. It does not edit the manifest.

### TESTED → ENABLED

Required:

1. Provider is already `TESTED`.
2. Activation evidence remains complete and matches current adapter version.
3. Explicit `ENABLED` approval is recorded.
4. Runtime health is fresh and exactly `OK`.
5. Trust/risk gates remain activatable.

Only after those checks should a reviewed manifest change set:

`lifecycleStage: 'ENABLED'` and `enabled: true`.

## Network ↔ asset safety

Flat provider asset lists are not sufficient for multi-chain execution.

Phase 4D adds exact `networkAssetSupport` rows so, for example, Ethereum Sepolia USDC cannot be accepted on an Arc Testnet route merely because both addresses appear in the same provider manifest.

Mainnet candidates are also mapped to their exact per-chain USDC deployment, but remain disabled.
